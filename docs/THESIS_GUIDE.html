Literature Review
Auction theory, existing platforms comparison, and technology justification
2.1 Auction Theory
Write this — all these map directly to your code
  • English Auction (Ascending Price): Bidders openly raise bids until no higher bid is placed — this is the model you implemented. Winner pays their highest bid.
  • Reserve Price: Minimum acceptable price set by seller. In your code: Product.reservePrice field.
  • Bid Increment: Minimum amount each new bid must exceed the previous. In your code: Product.minIncrement field.
  • Buy-Now Price: Fixed price that immediately ends the auction. In your code: Product.buyNowPrice and /api/product/:id/buy-now endpoint.
  • Deposit as Commitment Device: Academic literature suggests requiring a deposit reduces frivolous bids and bid sniping. Your system requires a 10% deposit for items ≥ ₮500,000.

2.3 Technology Justification
Why these technologies? (Write one paragraph per choice)
  • Node.js + Express: Non-blocking I/O ideal for real-time auction events; large npm ecosystem; same language (JS) across frontend and backend
  • MongoDB: Flexible schema supports different product types (regular items vs. vehicles with VIN/make/model). No schema migration needed when adding vehicle-specific fields
  • Socket.IO: WebSocket-based real-time communication. Compared to polling, reduces server load and provides <100ms bid update latency
  • React Native + Expo: Single codebase for cross-platform mobile. Expo SDK 54 provides image picker, camera (for KYC), and push notification APIs out of the box
  • JWT Authentication: Stateless tokens reduce database lookups per request. 1-day expiry with phone-auth refresh token rotation balances security and UX
  • Firebase FCM: Industry-standard push notification service. Free tier sufficient for project scale; supports both Android and future iOS
  • Cloudinary: CDN-backed image storage with automatic optimization. Prevents large image files from slowing the MongoDB database

3.3 Authentication Design
Describe the 5 authentication methods (all implemented)
  1. Email + OTP: POST /api/users/send-code → 6-digit OTP (10 min TTL) → POST /verify-email
  2. Phone SMS OTP: POST /api/auth/send-otp → Unitel/Mobicom/Skytel → 3 attempts per 10 min rate limit
  3. Google OAuth2: POST /api/users/google (web) / /google-mobile (mobile) using Google ID token
  4. eMongolia National ID: POST /api/users/emongolia — authenticates citizens via government portal, stores citizen data
  5. JWT Bearer: 1-day expiry token in cookie (web) or AsyncStorage (mobile). 401 auto-logout on mobile

3.4 Real-Time Bidding Design
Explain the race-condition problem and your solution
  • Problem: Two users bid simultaneously — both read currentBid = X, both submit X + increment. Without locking, one bid is silently overwritten
  • Solution in biddingService.js: MongoDB transaction + optimistic locking using __v (version key). findOneAndUpdate checks version before writing. Up to 3 retries on version conflict
  • Socket.IO events: bidUpdate and newBid broadcast to all connected clients after each successful bid. startAuctionCountdown sends per-second countdown
  • Auction Scheduler: node-cron runs every 60 seconds — activates scheduled auctions, ends expired auctions, releases held deposits
3.5 Deposit System Design
Step 1: Bidder checks deposit requirement
GET /api/deposits/check/:productId — returns required if price ≥ ₮500,000 threshold
Step 2: User accepts EULA
EULA middleware requireEulaAcceptance blocks deposit unless user has accepted current EULA version
Step 3: 10% deposit held from balance
POST /api/deposits — deducts from user balance, creates Deposit record with status held
Step 4: Auction ends → automatic release
Scheduler returns deposits to all bidders' balances. Winner pays via separate balance deduction

6.2 Architectural Evaluation
What worked well
  • 3-tier separation kept frontend/backend independently deployable
  • MongoDB flexible schema — added vehicle fields without breaking existing products
  • Socket.IO provided <100ms bid update latency vs. polling
  • Expo SDK 54 reduced mobile development time with built-in image picker and camera
  • node-cron scheduler reliably handled auction lifecycle without user action
Challenges & Solutions
  • Race conditions → solved with MongoDB optimistic locking + 3 retries
  • Multiple SMS carriers → abstract provider config via SMS_PROVIDER env var
  • High-trust transactions → deposit system + KYC verification badge
  • Rich-text on mobile → TipTap (web) + react-native-render-html (mobile)
